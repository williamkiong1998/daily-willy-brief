☕ Cold Open

The modern promise of an AI assistant is charmingly simple: give it a job, then get on with yours. The engineering question is less charming—and much more consequential: when it keeps working, who can stop it, what gets undone, and how do you know the stop actually took?

The Lead

The useful agent needs a stop button

Microsoft has introduced Autopilot, a persistent personal agent, alongside Copilot Managed Runtime, hosting infrastructure for code that runs inside a company’s Microsoft 365 environment. The company says the runtime is governed by IT and supports apps built in Cowork, Code and Copilot Studio; it is a launch claim, not evidence that every workflow is now safe. But the architecture points to a real product shift. A chat session ends with a reply. A persistent agent creates a lifecycle: queued work, data access, intermediate state, a final action and, ideally, a clean way to withdraw authority. For product teams, “always on” is not merely a capability. It is a contract for cancellation, accountability and recovery.

Why it matters: persistent work makes an agent more useful only if a user and an operator can still interrupt it without guessing what happens next.
The Takeaway
Autonomy changes the unit of design from an answer to a lifecycle. The right question is no longer “can the model do this?” but “can this work be started, observed, paused, cancelled and reconciled by the people who bear its consequences?”

Agent builders are being forced to define what “done” means
01
A new study finds merged AI coding-agent pull requests had 1.62× the odds of a verified follow-up fix versus comparable human PRs. The researchers tracked 6,774 agent PRs across 891 repositories; the paper is evidence, not a universal quality score. Its operational lesson is blunt: a merge is a checkpoint, not proof of completion. Treat review, monitoring and the first repair window as part of the agent’s job boundary.
02
OpenAI has set DevDay 2026 for 29 September in San Francisco. A date is not a product announcement, so there is nothing to benchmark yet. The signal is calendar-shaped: teams building on fast-moving platforms should separate an event from a dependency. Watch what ships, then test it against the workflow and evidence model you already own.
03
TM One argues that Malaysian enterprises need unified visibility as AI compresses the time available to spot and respond to threats. That is a company view, but it names the right design pressure. A security product that reports an incident after an autonomous workflow has already crossed systems is an audit trail, not a control loop. Put observable checkpoints upstream of irreversible actions.

🧠 Builder’s Notebook
Cancellation semantics: stopping is a product feature
Intuition: cancellation semantics means defining exactly what “stop” means at every point in a workflow. Think of a restaurant order: cancelling before the kitchen starts is different from cancelling after the dish is plated, and different again from reversing a completed card charge. “Stop” is not one button; it is a promise about state, cost and recovery.

Mechanism:
request → work starts → cancel signal → safe checkpoint → compensate or confirm → auditable final state
An agent needs cooperative checkpoints between tool calls, a deadline, and a durable record of whether a downstream action happened. For actions that cannot be undone—sending money, deleting data, publishing copy—the right cancellation policy may be “stop before commit.” For reversible work, the system needs a compensating action and a clear owner. This is why persistent agents require more than background execution.

Try this (20 min): take one automation you use today and draw three moments: before its external action, during it, and after it. For each, write: who may cancel, what state survives, what cost is already incurred, and what evidence proves the final outcome. If any answer is “we would check manually,” you have found the next product requirement.
