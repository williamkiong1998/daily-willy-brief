The new bottleneck in agent building is not finding a clever prompt. It is knowing what, exactly, you are importing into a system that can touch customer data, production code and external tools.
The Lead
Agent skills are becoming a supply chain before they become a standard.
A new GitSkills dataset counted 3.8 million public SKILL.md files across 282,200 GitHub repositories, collapsing to 1.88 million distinct contents by exact hash. A skill is just natural-language workflow guidance that an agent may select at run time; it is neither compiled nor centrally packaged. That makes the explosion useful and awkward. Reuse lets teams ship operational knowledge faster, but a copied instruction folder can quietly prescribe tools, credential handling, data movement or deployment steps. Meanwhile, one live catalog tracks 59,639 skills and 9,676 MCP servers. These are directory counts, not a security audit.

Why it matters: agent skills are turning into dependencies. Treat their provenance and permissions with the same seriousness as a new production library.
The Takeaway
A skill is not merely a prompt template. It is executable policy in prose: it tells a capable system which actions seem normal. The work now is to make origin, scope and change history visible before adoption outruns review.

🧠 Builder’s Notebook
Provenance contracts: make imported instructions inspectable
Intuition: provenance is the passport attached to a dependency: who issued it, what journey it took and whether it changed on the way. A skill needs the same treatment because its prose can shape real actions. A nice README is an introduction; provenance is the evidence you need when it asks an agent to use a secret or deploy a change.

Mechanism:
source and version → review of actions and permissions → approved scope → logged execution → revocation path
Put a name, commit hash and owner beside the skill. Then separate what it may read, write and call from what it merely describes. The quiet win is reversibility: if the source changes or misbehaves, you can disable one known version rather than hunt copied folders across projects.

Try this (20 min): pick one installed skill or MCP server. Record its repository, pinned version, owner, data it can access, external actions it can take and the one condition that disables it. If you cannot fill a field, the integration is still a prototype.
🔧 Product Craft
Design the “what will this do?” moment
The GitSkills researchers point out that an agent selects a skill probabilistically from its description; no compiler verifies the choice. That makes the install screen a product surface, not paperwork. Borrow the shape of a good banking confirmation: show the action, affected scope and irreversible consequence before the user says yes. “Adds research tools” is vague. “Can read this workspace and make web requests; cannot send messages or edit production” is an interface contract. The operational lesson is that trust is designed at the boundary, in words a tired person can still evaluate.
